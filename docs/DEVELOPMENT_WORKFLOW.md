# TrustVault Development Workflow

## Purpose

This document defines the standard development workflow for the TrustVault project.

Every feature, enhancement, bug fix, and milestone should follow this process to maintain consistency, code quality, and a clean Git history.

---

# Development Philosophy

TrustVault is developed in small, reviewable milestones.

Each milestone should:

- Complete one logical objective.
- Be implemented on its own Git branch.
- Be reviewed before merging.
- Keep main production-ready at all times.

---

# Repository Structure

The repository is organised into:

- docs/ — Project documentation.
- source-data/ — Original source assets.
- public/ — Production-ready assets.
- app/ — Next.js application.
- components/ — Reusable UI components.
- data/ — Application data.
- lib/ — Shared utilities.

---

# Standard Workflow

## 1. Start from main

```bash
git checkout main
git pull origin main
```

---

## 2. Create a feature branch

Examples:

```bash
git checkout -b feature/marketplace
```

```bash
git checkout -b feature/dashboard
```

```bash
git checkout -b docs/add-roadmap
```

Branch naming:

- feature/
- docs/
- fix/
- refactor/

---

## 3. Open Claude Code

Claude Code should be launched from the project root.

Claude must read:

- docs/PROJECT_CONTEXT.md
- docs/ARCHITECTURE.md
- docs/CLAUDE.md
- docs/ROADMAP.md

before making changes.

---

## 4. Scope every prompt

Each prompt should:

- Complete only one milestone.
- Avoid unrelated changes.
- Avoid feature creep.
- Stop when finished.

Never ask Claude to complete multiple milestones in one prompt.

---

## 5. Review changes

Before committing, review:

- New files
- Modified files
- Folder structure
- Documentation

Run:

```bash
git status
```

---

## 6. Run quality checks

Always verify:

```bash
npm run lint
```

```bash
npm run build
```

```bash
npm run dev
```

Open:

http://localhost:3000

Verify:

- No errors
- Correct layout
- Responsive behaviour

---

## 7. Commit changes

```bash
git add .
```

```bash
git commit -m "feat: description"
```

Use Conventional Commits:

- feat:
- fix:
- docs:
- refactor:
- chore:

---

## 8. Push

```bash
git push origin feature/...
```

---

## 9. Open Pull Request

Review:

- Files changed
- Documentation
- Folder structure

Merge only after verification.

---

## 10. Update main

```bash
git checkout main
```

```bash
git pull origin main
```

# AI Collaboration Guidelines

TrustVault is developed using AI-assisted software engineering.

Claude Code is treated as a development partner, not an autonomous developer.

Every AI-generated change must follow the standards below.

## 1. Read Project Documentation First

Before making any code changes, Claude must always read:

- docs/PROJECT_CONTEXT.md
- docs/ARCHITECTURE.md
- docs/CLAUDE.md
- docs/ROADMAP.md

Additional documentation should be read when relevant:

- docs/PRODUCT_CATALOG.md
- docs/ASSET_GUIDE.md
- docs/DESIGN_SYSTEM.md
- docs/DEVELOPMENT_WORKFLOW.md

These documents are the source of truth for the project.

## 2. One Milestone Per Prompt

Each prompt should complete only one milestone.

## 3. Respect the Roadmap

Claude should never begin a future phase unless explicitly instructed.

## 4. Never Assume Requirements

If documentation is unclear:

- Ask for clarification.
- Do not invent functionality.
- Do not guess business logic.

## 5. Explain Before Committing

Before any commit Claude should provide:

- Summary of changes
- Files modified
- Files created
- Dependencies added
- Validation completed
- Potential issues

## 6. Preserve Existing Architecture

Claude should extend the project and never reorganize or replace architecture without approval.

## 7. Prefer Reusable Components

Avoid duplicated code.

Create reusable components, utilities, and shared logic whenever appropriate.

## 8. Documentation First

Whenever architecture changes, update documentation before implementing additional features.

## 9. Production Quality

Generated code should be:

- Type-safe
- Accessible
- Responsive
- Maintainable
- Well documented

## 10. Never Modify Without Permission

Claude must never:

- Delete user assets.
- Rename Product IDs.
- Rename folders used by production.
- Change branding.
- Rewrite documentation without approval.

# Repository Conventions

These conventions apply throughout the TrustVault repository.

## Folder Naming

Folders use lowercase-kebab-case.

Examples:

- beauty
- home-kitchen
- oral-care
- gift-vault
- ai-marketplace

## File Naming

Documentation uses UPPERCASE_WITH_UNDERSCORES.md.

Examples:

- PROJECT_CONTEXT.md
- ARCHITECTURE.md
- ROADMAP.md
- DEVELOPMENT_WORKFLOW.md
- ASSET_GUIDE.md

## React Components

Use PascalCase.

Examples:

- Header.tsx
- MarketplaceCard.tsx
- WalletBalance.tsx

## Utilities

Use camelCase.

Examples:

- formatCurrency.ts
- getProduct.ts
- generateSlug.ts

## Product Images

Every product folder contains:

- cover.webp
- 1.webp
- 2.webp
- 3.webp

Never rename these files.

## Product Folder Naming

Product folders always use the Product ID.

Example:

- TV-BBW-000001

Never use product names as folder names.

## Categories

Categories follow lowercase-kebab-case.

Examples:

- beauty
- sports
- digital
- home-kitchen
- oral-care

## Source Assets

Original assets belong in source-data/.

Production assets belong in public/.

Never edit production assets directly.

## Product Catalogue

The master catalogue is:

- source-data/excel/TrustVault Product Catalogue.xlsx

This workbook is the single source of truth for:

- Product IDs
- Categories
- Prices
- Inventory
- Metadata

## Git Branches

Use:

- feature/
- docs/
- fix/
- refactor/
- chore/

## Commit Messages

Follow Conventional Commits.

Examples:

- feat: build marketplace layout
- docs: update asset guide
- fix: correct product card spacing
- refactor: simplify header component

## Dependencies

Only install dependencies required for the current milestone.

Avoid unnecessary packages.

## Public Assets

Everything inside public/ is production-ready.

Do not place temporary files here.

## Source Assets

Everything inside source-data/ is editable source material.

Files here are never served directly to users.

## README Files

Major folders should contain a README explaining:

- Purpose
- Contents
- Usage
- Related folders

This keeps the repository self-documenting.
